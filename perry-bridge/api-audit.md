# API audit — Node / npm surface reached by the `devcontainer.json` slice

Generated by tracing imports from the two entry points that actually matter for
Tauri integration:

- `readDevContainerConfigFile` in `src/spec-node/configContainer.ts`
- `getDevcontainerMetadata` in `src/spec-node/imageMetadata.ts`

…and pruning every transitive import that does **not** lie on the
"read + JSONC parse + `updateFromOldProperties` + pre-container `substitute()`"
path. The pruned-out modules (Docker CLI, OCI registry, tarball streaming,
PTY, shell server, feature resolution, dockerfile parsing, image inspection)
are explicitly out of scope per `README.md`.

**Slice modules retained**

| Module                                                | Reason                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------ |
| `src/spec-configuration/configuration.ts`             | `DevContainerConfig` types, `updateFromOldProperties`        |
| `src/spec-configuration/configurationCommonUtils.ts`  | `FileHost`, `uriToFsPath`, `parentURI`, well-known paths     |
| `src/spec-configuration/editableFiles.ts`             | `fileDocuments`, `CLIHostDocuments`, `createDocuments`       |
| `src/spec-common/variableSubstitution.ts`             | `substitute`, `SubstitutionContext`                          |
| `src/spec-utils/workspaces.ts`                        | `workspaceFromPath`                                          |

`src/spec-utils/pfs.ts` is **not** retained — it imports `ncp` (transitive
heavy native deps) and we only need the `FileHost` interface declaration plus
`FileTypeBitmask`. The interface is re-declared in `host.ts` with identical
shape.

## Symbol-by-symbol classification

Legend:

- **A** — Perry-supported as-is.
- **B** — Needs a Rust shim via the host-call protocol.
- **C** — Needs a TS replacement local to `perry-bridge/`.

## Host-call surface (the contract for `PROTOCOL.md`)

The full set of operations the Rust side must implement is:

| op             | args                          | reply                              |
| -------------- | ----------------------------- | ---------------------------------- |
| `fs.readFile`  | `{ path: string }`            | `{ bytes: base64 string }`         |
| `fs.writeFile` | `{ path, bytes: base64 }`     | `{}`                               |
| `fs.stat`      | `{ path: string }`            | `{ kind: "file"\|"dir"\|"other", size: number }` or `{ kind: "missing" }` |
| `fs.readDir`   | `{ path: string }`            | `{ entries: [{ name, kind }] }`    |

That is **the entire wire surface** for the slice. No env, no homedir, no
spawn, no network. The caller (Tauri host or Cargo example) supplies env and
working directory through the JSON request envelope — see `PROTOCOL.md`.

## Re-plan triggers

Per the plan, the audit is the artifact that decides whether the slice is
viable. The audit is viable as written **only if** the Perry capability spike
(step 2) confirms:

1. `jsonc-parser` compiles and parses correctly.
2. `vscode-uri` compiles, or its single `process.platform` branch can be
   neutralised by the slice's exclusive use of `uriToFsPath(uri, platform)`.
3. Perry can express the line-delimited JSON stdin/stdout protocol described
   in `PROTOCOL.md`.

If any of those fail, the documented fallback is the `perry-bridge/src/uri.ts`
helper for (2) or a hand-rolled JSONC tokenizer for (1). No fallback is
defined for (3) because without a stdin/stdout channel the binary can't
communicate with its host at all and Perry would be the wrong tool — we'd
re-evaluate the whole approach, as called out under "Re-plan" in the original
plan.
